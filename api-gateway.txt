# API Gateway — AI Editor Setup & Implementation Specification

## Role

Act as a **Principal Backend Engineer, API Gateway Architect, Distributed Systems Engineer, and Cloud Infrastructure Engineer**.

You are responsible for designing and implementing a production-ready **`api-gateway`** for this microservices marketplace e-commerce platform.

The API Gateway is the **single public HTTP entry point** for client applications.

It must provide:

- request routing
- authentication enforcement
- authorization context propagation
- API versioning
- rate limiting
- request correlation
- security middleware
- request validation where appropriate
- timeout handling
- retry handling where safe
- service health visibility
- observability
- centralized error handling
- controlled access to internal microservices

Do **not** move business logic into the API Gateway.

The gateway should coordinate and protect traffic, not become another business service.

8. Authentication Architecture

The API Gateway must integrate with auth-service.

The gateway should NOT become the authentication source of truth.

Architecture:

Client
   ↓
API Gateway
   ↓
validate access token
   ↓
forward authenticated identity
   ↓
downstream service

auth-service remains responsible for:

login
passwords
refresh tokens
OAuth
MFA
identity
token issuance

The gateway is responsible for validating the authentication context required for protected routes.

9. Token Validation

Prefer validating signed access tokens using the appropriate trusted signing configuration.

Support:

JWT verification
issuer validation
audience validation
expiration validation
signature validation

Do not trust arbitrary headers such as:

x-user-id
x-role
x-admin

from public clients.

If the gateway injects identity headers for downstream services, first remove any client-supplied versions.

Example internal headers:

x-request-id
x-user-id
x-user-roles
x-authenticated

Only the gateway or trusted internal infrastructure should set these.

10. Authentication Context Propagation

After authentication:

Client
   ↓

   ↓

   ↓
Downstream Service

Propagate:

user_id

roles
scopes
tenant_id where applicable
request_id
trace_id

Only propagate claims actually required by downstream services.

Do not forward the complete JWT unless there is a specific reason.

12. Role-Based Access Control

Do not implement business-domain permissions in the gateway.

The gateway may enforce coarse-grained access such as:

PUBLIC
AUTHENTICATED
ADMIN
SELLER
INTERNAL

Detailed authorization remains inside the owning service.

Example:

Gateway
→ user must be authenticated

seller-service
→ user must own seller account

payment-service
→ user must be authorized for payment operation

This preserves proper service boundaries.

13. Rate Limiting

Implement Redis-backed rate limiting.

Different route groups should have different policies.

Example:

Authentication
→ strict

Public catalog
→ high allowance

Search
→ controlled

Cart
→ moderate

Checkout/payment
→ strict abuse protection

Admin
→ strict + authenticated

Do not blindly apply the same rate limit to every endpoint.

Support rate limits by:

IP
user ID
route
API key where applicable

Use the combination appropriate to the route.

14. Abuse Protection

Add protections for:

credential stuffing
login abuse
request flooding
large payloads
path abuse
invalid HTTP methods
oversized headers
repeated failed authentication

Do not create a complex WAF inside the application gateway.

Use infrastructure-level WAF/CDN capabilities where available.

15. Request Size Limits

Define route-sensitive payload limits.

Examples:

normal API JSON
→ small/medium payload

media
→ direct-to-S3 presigned upload

The gateway should not become the media upload bottleneck.

For large files:

Client
   ↓
media-service
   ↓
presigned URL
   ↓
S3 / MinIO

not:

Client
   ↓
API Gateway
   ↓
media-service
   ↓
S3

unless a specific security requirement requires proxying.

16. Request ID

Every incoming request should receive a request ID.

Behavior:

Client sends x-request-id
     ↓
validate/use if safe
     ↓
otherwise generate new ID
     ↓
attach to request context
     ↓
forward downstream

Every downstream request should receive the same correlation identifier.

Example:

x-request-id: req_01J...

Never trust arbitrary request IDs for security decisions.

17. Trace Propagation

Use OpenTelemetry trace propagation.

Example:

Client
  ↓
Gateway
  ↓
catalog-service
  ↓
product-service

One distributed trace should allow operators to see the complete request path.

18. Proxy Behavior

The gateway should forward:

HTTP method
path
query parameters
approved headers
body
request ID
trace context
authenticated identity context

Do not blindly forward every incoming header.

Explicitly control forwarded headers.

19. Header Sanitization

Remove or overwrite client-controlled internal headers such as:

x-user-id
x-user-roles
x-authenticated
x-internal-service
x-service-auth

before creating the trusted internal context.

Also handle hop-by-hop headers correctly.

20. Timeout Policy

Every downstream service request must have a timeout.

Do not allow an unavailable service to hold gateway connections indefinitely.

Example baseline:

catalog/search
→ short timeout

cart/order
→ moderate timeout

payment
→ carefully tuned timeout

recommendation
→ short bounded timeout

Use configurable timeouts.

21. Retry Policy

Retries must be conservative.

Retry only when:

operation is idempotent
failure is transient
request timeout policy allows it

Good retry candidates can include certain:

GET
HEAD
safe internal reads

Avoid automatic retries for:

POST payment
POST order
POST shipment
POST payout

unless explicit idempotency support exists.

Never blindly retry financial operations.

22. Circuit Breaker

Implement or integrate a circuit-breaker mechanism where justified.

Conceptually:

Healthy
   ↓
Failures increase
   ↓
OPEN
   ↓
fail fast
   ↓
HALF_OPEN
   ↓
test request
   ↓
Healthy / OPEN

Use circuit breaking for unstable downstream dependencies.

Do not create unnecessary complexity for services that are already highly reliable.

23. Service Unavailability

If a downstream service is unavailable:

Do not expose internal stack traces.

Return a consistent gateway response.

Example:

{
  "error": {
    "code": "SERVICE_UNAVAILABLE",
    "message": "The requested service is temporarily unavailable.",
    "requestId": "req_123"
  }
}

Do not expose:

database hostnames
internal IPs
service URLs
stack traces
connection strings
24. Error Normalization

Downstream services should have their own error models.

The gateway may normalize transport-level errors:

timeout
connection refused
service unavailable
invalid proxy response

Do not unnecessarily rewrite every domain error.

For example:

product-service
→ PRODUCT_NOT_FOUND

gateway
→ preserve domain error

while:

product-service unreachable

gateway
→ SERVICE_UNAVAILABLE

This prevents the gateway from hiding useful business errors.

25. API Versioning

Use versioned public routes:

/api/v1/...

Do not expose internal service versions directly unless required.

Example:

/api/v1/products

may internally route to:

product-service internal endpoint

This allows internal services to evolve independently.

26. Service Discovery

For the first implementation, support environment-based service URLs.

Example:

PRODUCT_SERVICE_URL=http://product-service:3000

Design the registry so it can later support:

Docker Compose service names
Kubernetes DNS
service mesh
external service discovery

Do not hard-code localhost assumptions into production configuration.

27. Gateway Route Registry

Create a central typed configuration.

Example concept:

type GatewayRoute = {
  prefix: string;
  target: string;
  auth: 'public' | 'authenticated' | 'admin';
  timeoutMs?: number;
  rateLimit?: {
    limit: number;
    windowSeconds: number;
  };
};

Routes should be declarative.

Avoid large collections of custom route handlers that simply repeat proxy code.

28. API Aggregation

The gateway may expose a small number of read-oriented aggregation endpoints when that materially reduces frontend complexity.

Example:

GET /api/v1/home

could combine:

catalog
recommendations
promotions

However:

keep aggregation limited
avoid embedding business rules
avoid turning the gateway into a monolithic backend
protect against fan-out latency

Use aggregation only where there is a clear client/API benefit.

29. Do Not Put Business Logic in the Gateway

Do not implement:

cart totals
payment calculations
inventory reservations
order state transitions
promotion rules
commission calculations
shipping business rules
recommendation algorithms
seller settlement logic

inside the gateway.

The gateway should answer:

Where should this request go, is the caller allowed to call it, and can the request safely reach the target service?

30. Caching

Gateway-level caching should be limited.

Potential candidates:

public catalog GET
public category GET
public configuration GET

Avoid caching:

payments
cart
checkout
order creation
user-private information

unless there is an explicit strategy.

Prefer service-level caches where domain semantics are important.

31. CORS

Configure CORS explicitly.

Do not use:

Access-Control-Allow-Origin: *

for authenticated production APIs unless there is a justified public use case.

Use configured origins per environment.

Example:

CORS_ALLOWED_ORIGINS=https://example.com,https://app.example.com
32. Security Headers

Apply appropriate security headers at the gateway.

Consider:

Content-Security-Policy where applicable
X-Content-Type-Options
Referrer-Policy
X-Frame-Options
Strict-Transport-Security in HTTPS deployments

Do not blindly apply browser-specific policies to APIs without testing compatibility.

33. HTTP Methods

Reject unsupported methods explicitly.

Expected methods:

GET
POST
PUT
PATCH
DELETE
OPTIONS
HEAD where appropriate

Do not allow arbitrary methods through the proxy.

34. Internal Service Security

Do not assume internal services are automatically trusted.

Where possible:

TLS/mTLS
internal network isolation
service authentication
trusted internal headers
network policies

The gateway should be the public entry point, but internal services should still protect themselves.

35. Public Exposure

api-gateway

to the public application network.

Keep:

auth-service
product-service
order-service
payment-service

shipping-service

43. Kafka

Kafka is not required for normal HTTP routing.

Do not put every HTTP request onto Kafka.

Use Kafka only for gateway events that have a real architectural use case, such as:

gateway.security_event
gateway.rate_limit_event
gateway.audit_event
gateway.authentication_failure

Avoid creating Kafka dependencies merely because the platform already uses Kafka.

44. Audit Events

Where required, the gateway may publish security/audit events such as:

authentication.failed
rate_limit.triggered
admin.route.accessed
security.policy.blocked

The dedicated audit-service can consume those events.

Do not publish every successful GET request as a Kafka event.

49. Timeout and Retry Matrix

Use different policies by operation type.

Operation	Retry by default
GET catalog	Yes, limited
GET search	Yes, limited
GET product	Yes, limited
GET recommendations	Limited
POST cart item	No by default
POST order	No
POST payment	No
POST shipment	No
DELETE resource	Depends on idempotency

Every retry policy must account for idempotency.

50. Security Boundary

The API Gateway is a security boundary, not the only security layer.

Use:

Internet
   ↓
Load Balancer / CDN / WAF
   ↓
API Gateway
   ↓
Internal services

Where the infrastructure supports it.

Do not attempt to replace a dedicated WAF with application middleware alone.

59. Performance

Optimize for:

low proxy latency
efficient connection reuse
bounded memory usage
high concurrent connections
low Redis latency
minimal gateway logic

Do not perform expensive transformations in the gateway.

# Monorepo Engineering & Architectural Rules (`docs/RULES.md`)

This document is the authoritative standard for all engineering practices, architecture boundaries, and code standards across the **Larekmart** platform. Every engineer and AI coding agent working in this repository MUST comply with these rules.

---

## 1. Architectural Boundaries & Dependencies

1. **Dependency Direction**:
   - Applications (`apps/*`) depend on shared internal packages (`packages/*`).
   - Packages NEVER depend on applications.
   - Applications NEVER import code from other applications directly.
   - Cross-service data exchange happens strictly through asynchronous **Kafka events** or public **API Gateway reverse proxy** routing.
2. **Shared Contract Package (`@repo/types`)**:
   - All domain interfaces, cross-service payload types, Zod validation schemas, and Kafka event contracts MUST reside in `@repo/types`.
   - Never duplicate interfaces, enums, or Zod schemas within individual microservices.
3. **Database Isolation & Model Ownership**:
   - Each backend service strictly owns its database and schema:
     - `@repo/product-db` (Prisma / PostgreSQL): `product-service`
     - `@repo/inventory-db` (Prisma / PostgreSQL): `inventory-service`
     - `@repo/catalog-db` (Prisma / PostgreSQL): `catalog-service`
     - `@repo/shipping-db` (Prisma / PostgreSQL): `shipping-service`
     - `@repo/user-db` (Prisma / PostgreSQL): `user-service`
     - `@repo/order-db` (Mongoose / MongoDB): `order-service`
     - `@repo/cart-db` (Mongoose / MongoDB): `cart-service`
     - Drizzle ORM (`media_db` / PostgreSQL): `media-service`
   - Services must NEVER connect to or query another service's database directly.
4. **Never Edit Generated Database Code**:
   - Code inside `generated/prisma/**` is generated by `prisma generate` and is gitignored. Always edit `schema.prisma` and run migration scripts.

## 2. Service Communication & Kafka Event Conventions

1. **No Service-to-Service Synchronous HTTP**:
   - Backend services must never make internal synchronous HTTP requests to one another.
   - Cross-service orchestration is event-driven through Kafka.
2. **Strict Kafka Message Envelope**:
   - Every producer MUST emit messages conforming to the standard envelope:
     ```ts
     await producer.send(TOPIC_NAME, { value: payload });
     ```
   - Every consumer MUST deserialize from `message.value` rather than inspecting raw message roots:
     ```ts
     const payload = JSON.parse(message.value.toString());
     ```
3. **Consumer Loop Resiliency**:
   - Kafka handlers must catch and log processing errors so a malformed or poisoned event never crashes the consumer loop.
   - Dead-letter queue classification or structured error logging must be applied on exhausted retries.
4. **Event Documentation Sync**:
   - Whenever adding or updating a Kafka event:
     - Add the type and Zod schema to `@repo/types`.
     - Update the producer and all consumers simultaneously.
     - Document the payload and lifecycle in `docs/EVENT-DRIVEN-ARCHITECTURE.md`.
5. **Transactional Outbox for Dual Writes**:
   - Microservices committing database mutations that trigger downstream Kafka events must write domain events atomically to an `OutboxEvent` model/table within the same transaction.
   - Dual-writes directly to Kafka outside the database transaction are strictly prohibited.
6. **Distributed Mutation Idempotency**:
   - High-impact state-mutating HTTP requests (e.g., checkout mutations, order creations, payments) must enforce client-supplied `Idempotency-Key` headers.
   - Mutual exclusion must be acquired via Redis atomic leases (`acquireIdempotencyLock`) to prevent duplicate writes and safely replay cached responses with `Idempotent-Replayed: true`.
7. **Thundering Herd Shielding (`SingleFlight`)**:
   - Aggregation routes and high-velocity read endpoints prone to cache misses must coalesce concurrent in-flight promises via `SingleFlightGroup` before initiating downstream network fetches.

## 3. Authentication & Security Rules

1. **Clerk Authentication Everywhere**:
   - All authentication is handled through Clerk (`@clerk/nextjs` for frontends, Clerk Backend SDK for microservices).
   - Never hand-roll custom JWT verification, passwords, or session management.
2. **Identity Derivation**:
   - Never trust client-supplied `userId`, `email`, or customer identity in request bodies or query params.
   - Always derive `userId` from verified session claims (`auth().getToken()` or verified JWT).
3. **Role-Based Authorization (RBAC)**:
   - Protected user routes must enforce `shouldBeUser`.
   - Admin routes must enforce `shouldBeAdmin` by checking `sessionClaims.metadata.role === "admin"`.
4. **Stripe & Payment Integrity**:
   - Webhooks in `payment-service` MUST verify the Stripe raw signature using `stripe.webhooks.constructEvent` with `STRIPE_WEBHOOK_SECRET`.
   - Public keys (`NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`) are client-safe; secret keys (`STRIPE_SECRET_KEY`) must NEVER be leaked to frontends or exposed via `NEXT_PUBLIC_*`.
5. **No Committed Secrets**:
   - Never commit real `.env` or `.env.local` files to git.
   - All environment variables must have sanitized placeholders in corresponding `.env.example` files.

## 4. Frontend Standards (`apps/client` & `apps/admin`)

1. **React Server Components (RSC) First**:
   - Components and pages are Server Components by default.
   - Add `"use client"` only when utilizing client hooks (`useState`, `useEffect`, `useRef`), browser APIs, or interactive event listeners.
2. **Animation Boundaries (Framer Motion & GSAP)**:
   - **Allowed Framer Motion Scope**: Exclusively client-side overlays, slide-overs, modals, and workflow step transitions unmounted on initial render (`CartDrawer`, `WishlistDrawer`, `QuickViewModal`, and multi-step cart transitions in `cart/page.tsx`).
   - **Prohibited Framer Motion Scope**: NEVER use `<motion.button>` or dynamic `layoutId` on high-cardinality static SSR product or category grids (`ProductCard`, `CategoriesClient`, `FlashDeals`). The server renderer injects attributes (`tabindex="0"`, `data-motion-id`) that clash with React 19 hydration.
   - **Hardware-Accelerated CSS**: For static product grids, use GPU-composited Tailwind CSS transitions (`transition-all duration-300 hover:scale-[1.02] active:scale-95`).
   - **GSAP Timelines**: Reserved for complex entrance sequences and promotional banner carousels (`HeroBanner.tsx`).
3. **SSR Hydration Resilience (React 19 & Next.js 16)**:
   - Guard `localStorage`-backed Zustand stores (`wishlistStore`, `cartStore`) with an `isMounted` state flag before rendering client-dependent attributes.
   - Add `suppressHydrationWarning` on SVG icons to protect against browser extensions injecting attributes like `data-motion-id`.
   - Add `suppressHydrationWarning` on live countdown tickers and date-derived elements (`FlashDeals.tsx`).
4. **Mobile & Cross-Screen Responsiveness**:
   - Design mobile-first across breakpoints (`320px–480px` mobile, `640px–768px` tablet, `1024px` laptop, `1280px+` desktop).
   - Ensure omnibars, drawers, and modal dialogs adapt without horizontal clipping.
   - Provide touch-friendly tap targets (minimum 40x40px).

## 5. TypeScript & Code Standards

1. **Strict Type Safety**:
   - Enforce `strict`, `noUncheckedIndexedAccess`, and `isolatedModules` defined in `@repo/typescript-config/base.json`.
   - Never use `any` or `@ts-ignore` to silence type warnings. Use `unknown` with runtime type narrowing or Zod schemas.
2. **Explicit ESM Module Imports**:
   - Backend services output Node ESM (`"type": "module"`). Follow the file's extension convention (`.js` extension where required).
3. **Structured API Error Responses**:
   - Microservices must return consistent JSON bodies `{ message: string }` accompanied by standard HTTP status codes (`400`, `401`, `403`, `404`, `429`, `500`).
4. **Health & Readiness Probes**:
   - HTTP services must implement `GET /health` (dependency status for Postgres, Mongo, Redis) and `GET /ready` (traffic acceptance check).

## 7. The 360° Feature Delivery Standard (Mandatory Vertical Execution Playbook)

Whenever a new feature or service is built (e.g. `review-service`, customer return portal, promotion engine), it MUST execute across all 8 layers without omitting any layer:

```
[1. Contracts & Types] -> [2. Backend Service & Outbox] -> [3. API Gateway Routing & Policies]
         ↓
[4. Kafka Event Streams & DLQ] -> [5. Client Storefront UI] -> [6. Admin Operations UI]
         ↓
[7. Automated Unit/Integration Tests] -> [8. Security & Zero-Trust Audit]
```

### 1. Schema & Contract Foundation (`@repo/types`, DB Schema)
- Define canonical TypeScript interfaces and Zod validation schemas in `packages/types/src/<domain>.ts`.
- Export schemas and types in `packages/types/src/index.ts`.
- Create or update the service database schema (Prisma or Drizzle). Generate clients/types via migration scripts.
- Never duplicate type declarations or validation schemas inside individual application directories.

### 2. Backend Microservice Architecture (`apps/<service>`)
- Structure: `routes/` -> `controllers/` -> `services/` -> `repositories/` (or ORM models).
- Enforce transactional outbox (`OutboxEvent`) for any database mutations that produce asynchronous domain events.
- Implement distributed mutation idempotency (`Idempotency-Key` + Redis atomic lease) for high-impact mutations.
- Implement readiness/health probes (`/health`, `/ready`) checking database and messaging dependencies.

### 3. API Gateway Reverse Proxy & Resilience (`apps/api-gateway`)
- Register prefixes in `public.routes.ts`, `authenticated.routes.ts`, or `admin.routes.ts`.
- Configure service target URLs, upstream timeouts, and circuit breaker registrations.
- Wrap cacheable or high-velocity aggregation read paths with `SingleFlightGroup` to shield backends from thundering herds.
- Unconditionally strip client-supplied identity/claim headers at the gateway before forwarding verified identity headers (`x-user-id`, `x-user-role`).

### 4. Kafka Event Lifecycle & Poison-Pill Resilience (`@repo/kafka`)
- Producers must use `{ value: payload }` envelope and produce via transactional outbox.
- Consumers must extract `message.value` and register Dead-Letter Queue (DLQ) isolation (`<topic>.dlq`) for unrecoverable errors (`SyntaxError`, `ZodError`).
- Update `docs/EVENT-DRIVEN-ARCHITECTURE.md` with new event payloads, producers, and consumers.

### 5. Customer Storefront Implementation (`apps/client`)
- Build client service in `apps/client/src/services/<domain>.service.ts` communicating with the backend via API Gateway (`process.env.NEXT_PUBLIC_API_GATEWAY_URL`).
- Build responsive, accessible UI pages and components adhering to the Larekmart design system (dark/light mode, Tailwind CSS transitions, micro-animations).
- Maintain React 19 / Next.js 16 hydration safety: avoid motion layout IDs on static grids, guard client-only localStorage states with `isMounted`, and use Server Components by default.

### 6. Admin Backoffice Operations (`apps/admin`)
- Build admin service in `apps/admin/src/services/<domain>.service.ts`.
- Implement responsive dashboards with KPIs, searchable/filterable data tables, action modals (approval, rejection, inspection, override), and audit notifications via React Query.
- Ensure admin routes are secured behind Clerk admin authorization.

### 7. Automated Unit & Integration Testing
- Add standalone test suites under `tests/` in the service or app.
- Never introduce Jest or Vitest; follow the repository's native tsx test runner pattern.
- Cover normal execution flows, validation rejections, duplicate request replay, and boundary failure modes.

### 8. Security & Zero-Trust Hardening
- **Zero-Trust Identity**: Never trust client-supplied user IDs in bodies/params. Extract strictly from verified Clerk tokens.
- **IDOR Protection**: Verify that the authenticated customer strictly owns the target resource before returning or mutating records.
- **Constant-Time Verification**: Microservice internal endpoints must verify `x-internal-secret` using constant-time string comparisons.
- **Input & Asset Sanitization**: Validate media URLs against authorized S3/MinIO bucket domains; sanitize freeform text inputs.
- **CI/CD & Documentation**: Update `AGENTS.md`, `README.md`, OpenAPI/plans, and ensure GitHub Actions workflow checks pass cleanly.
